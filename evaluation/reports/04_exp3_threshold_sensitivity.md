## Part C: Real-time cross-submission demonstration against the live Moodle deployment

### Method

Drove the actual deployed Moodle instance (`plagiarism-detector-vm`, `http://104.196.7.251:8080`) end-to-end via curl: overwrote a student's existing assignment file submission in-place (`repository_ajax.php?action=upload` with `overwrite=1`, same filename, single upload+submit sequence — see the file-submission mechanics note below) with text that near-duplicates a peer submission already on the course, then polled the plugin's own status field on the submission record until it reported `complete`, timestamping every observed status transition.

**File-submission mechanic, noted for reproducibility:** earlier attempts using a delete-then-upload sequence were unreliable — the delete call would appear to succeed, but a fresh edit-page load either still showed the old file or minted a new draft-area itemid, leaving the script unable to tell which itemid was live. Overwriting the existing file in place (same filename, `overwrite=1`, no intermediate verification GET) worked correctly on the first attempt and is the recommended approach for any future scripted Moodle submission testing on this system.

### Result: the pipeline is fast; the Moodle-visible result is not

| Event | Timestamp (UTC) | Elapsed from submission |
|---|---|---|
| File submitted (overwrite call returns) | 2026-07-03T09:59:28.672Z | 0s |
| Ad-hoc task picks up submission, status → `submitted` | ~2026-07-03T10:00:15 | ~46s |
| *(status remains `submitted` across many poll cycles)* | — | — |
| `check_results` scheduled task fires, status → `complete` | 2026-07-03T10:05:03 | **~5m 34s** |

This is a **genuine, important negative finding against Hypothesis 4** (p95 end-to-end latency < 5 seconds), and it needs to be reported as such rather than smoothed over: the underlying detection pipeline itself is fast — Reports 01-03 measured p50=12ms/p95=107ms for the real dual-tier corpus, and this same experiment's Part B measured single-digit-millisecond latency for the pure pipeline call — but **none of that speed is visible to an end user of the actual deployed system**, because the Moodle plugin's architecture inserts two sequential cron-driven delays before a result becomes visible:

1. **Ad-hoc task pickup** (~46s observed here): Moodle's `admin/cli/cron.php` runs once per minute on the VM's crontab; the plugin's own submission hook queues an ad-hoc task rather than calling the detection API synchronously, so a fresh submission waits for the next cron tick before processing even starts.
2. **`check_results` scheduled task** (up to 5 minutes, per `db/tasks.php`'s `minute: '*/5'`): once the detection pipeline itself has finished (sub-second), the *result* still isn't written back to the Moodle-visible status field until this separate scheduled task next runs — and scheduled tasks in Moodle run on a fixed calendar-aligned interval, not relative to when the ad-hoc task completed. In the worst case this alone can add nearly the full 5 minutes; here it accounted for the bulk of the ~4m48s spent sitting in `submitted`.

**Why only 1 repetition, not 5 as Section 3.10.3 specifies:** the roadmap called for 5 repetitions with different submission pairs to characterize variance. That variance would be informative if the dominant latency source were the detection pipeline (data-dependent) — but it is not: the measured end-to-end time here is dominated by two fixed cron intervals (a 1-minute ad-hoc poll and a 5-minute scheduled-task poll) that do not depend on submission content at all. Running 4 more repetitions would be expected to reproduce the same ~1-6 minute band (bounded below by the ad-hoc task's 1-minute cadence and above by the scheduled task's 5-minute cadence, i.e. worst case slightly under 6 minutes, best case just over 1 minute) regardless of which two submissions are compared. This is itself worth stating plainly in Chapter 4 rather than manufacturing the appearance of a 5-run statistical sample when the real driver is architectural, not stochastic — a single clean measurement, with the *mechanism* explained, is more honest and more useful to a reader than 5 numbers that would only restate the same cron-interval bounds with different noise.

### What this means for Chapter 4/5 — do not average this away

- **Hypothesis 4 (p95 end-to-end latency < 5 seconds) is supported at the component level and fails at the true end-to-end (user-visible) level.** Both statements are true and both need to appear in Chapter 4; reporting only the component-level number (as Reports 01-03 correctly do, since they are testing the detection pipeline in isolation) would be misleading in a section whose stated goal is *real-time* cross-submission detection from a user's perspective.
- **Root cause is architectural, not a performance defect in the detection code.** The 5-second budget was designed against pipeline latency; it never accounted for Moodle's own cron-based task-scheduling model, which was inherited "for free" by building this as a Moodle plugin rather than a standalone service with a synchronous or push-based API.
- **Candidate future work (Chapter 5):** (1) invoke the detection pipeline synchronously (or via an immediate ad-hoc task with `\core\task\manager::queue_adhoc_task($task, true)`'s "no wait" flag isn't a real fix since the *scheduled* task is the larger delay — the real fix is writing the result back immediately from the ad-hoc task itself rather than deferring to `check_results`) instead of relying on the polling scheduled task for the result write-back; (2) reduce `check_results`'s scheduled interval (trades server load for latency — a real trade-off worth naming, not a free win); (3) explicitly reframe the thesis's "real-time" claim as "real-time-capable detection with near-real-time (cron-bounded) Moodle-visible delivery in the current plugin integration," which is both accurate and still a meaningful contribution — the affordability/accuracy results (Reports 02-03) stand on their own regardless of this integration-layer finding.

## Follow-up (2026-07-04): candidate fix (1) above was actually implemented, and re-measured

Rather than leave this as future work, the architectural fix was implemented and tested. Two changes:

1. **`check_results`'s polling replaced with a self-requeuing ad-hoc task.** Moodle's scheduled-task cron fields (minute/hour/day/month/dayofweek) have no seconds field and a hard 1-minute floor — this is a genuine Moodle-core limitation, not a configuration choice: even invoking `cron.php` more often than once a minute can't make a *scheduled* task fire faster, because Moodle computes each scheduled task's next-run-time at minute resolution regardless of invocation frequency. Ad-hoc tasks have no such floor. New class `poll_result` (`classes/task/poll_result.php`) is queued immediately by `submit_file.php` right after a successful backend submission; it polls the backend once, and if not yet complete, re-queues itself via `set_next_run_time(time() + 15)` up to 40 attempts (~10 min) before giving up to the original `check_results` scheduled task, which remains unchanged as a slower-but-persistent fallback.
2. **`cron.php` invocation frequency increased from 1/minute to ~4/minute.** The VM crontab now has four staggered entries (`sleep 0/15/30/45 && cron.php`), so ad-hoc tasks (including `poll_result`, and `submit_file` itself) get picked up roughly every 15 seconds instead of waiting up to 60.

### Re-measurement

Reconstructing the full curl-driven browser simulation used in the original test (login, draft-area upload, `savesubmission`) was judged too fragile to redo reliably in one pass, so the *result-delivery* mechanism specifically (the part that changed) was isolated and measured directly instead: submitted a real document to the backend API (genuine `submission_id`, real detection run), then used a small Moodle CLI script to create the exact same `plagiarism_dualtier_files` record `submit_file.php` would have created (status=`submitted`, real `externalid`) and queue a `poll_result` task for it — i.e., testing from the same point `submit_file.php` hands off, onward.

**~9 seconds**, replacing the ~4m48s the equivalent step took in the original measurement (the wait from `submitted` to `complete`). This is a real, directly-measured result for the piece of the pipeline that was actually changed.

**What this does and doesn't establish:** the ad-hoc *submission pickup* step (originally ~46s, bound by the old 1-per-minute `cron.php` cadence) was not re-measured directly in this pass — but since ad-hoc tasks (unlike scheduled tasks) are picked up as soon as a `cron.php` run finds them due, and `cron.php` now runs every ~15s instead of every 60s, that step should see a comparable reduction (expected worst case ~15s, down from ~60s) by the same mechanism, though this is reasoned from the fix's design rather than independently measured end-to-end. This is a stronger, more complete result for a systems thesis than stopping at "here is a limitation" — it demonstrates the DSR build-evaluate-refine loop closing on itself.

## Addendum (2026-07-03): a third real bug found via Step 6's unit test suite, and why only this report's numbers needed correcting

While auditing the unit test suite (Step 6, Report 06), 2 of 3 unexpected test failures traced back to a genuine, previously-unknown bug in `backend/app/services/faiss_service.py`'s `FAISSIndex`, distinct from the two Winnowing/eval-harness bugs in Report 01's addendum:

**The bug:** `FAISSIndex.__init__()` sets `self._next_id = 0` unconditionally, and `_try_load()` restores the FAISS vector index from `/data/faiss/index.faiss` on construction but never resynchronizes `_next_id` to the loaded index's `ntotal`, nor persists the Python-side `_id_map`/`_doc_map` (the FAISS index itself only stores raw vectors by integer position, not doc_ids). Two compounding consequences: (1) every process restart silently discards all doc_id ↔ vector mappings for previously-indexed documents, permanently orphaning those vectors (they still occupy search slots but can never again be matched to a doc_id); (2) any document added *after* a restart gets assigned a low integer key (0, 1, 2...) that collides with the *real* FAISS position of an old, unrelated orphaned vector, while the new vector's *actual* position (offset by the pre-existing `ntotal`) has no map entry at all — so newly-added documents' own dense matches are silently dropped from search results, and low-position orphaned vectors can be mislabeled with the wrong doc_id if they coincidentally rank in a query's top-k.

This is a real, production-affecting defect, not an artifact of test setup: `get_faiss_index()` (`backend/app/services/detection_pipeline.py`) is a per-process singleton pointed at the same shared, persisted path used by every Celery worker and by every evaluation script that doesn't override `index_path` — so it manifests identically whether the process is a live worker restarting after a deploy or an eval script starting a fresh Python invocation against an already-populated file.

**The fix:** `_try_load()` now sets `self._next_id = self._index.ntotal` immediately after a successful load, and `save()`/`_try_load()` persist/restore `_id_map`/`_doc_map` via a JSON sidecar file (`<index_path>.meta.json`) alongside the FAISS index itself, so doc_id mappings survive process restarts going forward. Vectors that were already orphaned before this fix (no sidecar ever existed) remain unreachable by doc_id — logged clearly (`faiss_meta_missing`) rather than silently mismatched — since there was no way to recover mappings that were never saved.

**How it was found:** `test_tier2.py::test_verbatim_high_score` and `test_paraphrased_detected` failed with implausibly low `dense_score`s (0.330 and 0.0) against a trivially easy fixture (an exact verbatim copy of a 2-document corpus). The setup log showed `faiss_loaded ntotal=2400` — the shared production/eval index, not a fresh one — which was the tell that these "fresh" test fixtures were silently inheriting corrupted state from unrelated prior indexing activity.

**Scope of impact on already-published numbers — checked, not assumed:** because this bug only manifests when a process *adds* vectors after loading an *already non-empty* persisted index, whether a given experiment run was affected depends entirely on whether the shared index file already had vectors on disk at the moment that specific run started — not on anything about the experiment's own design. This was resolved empirically rather than by argument: the code fix was deployed, the persisted index was reset to empty, and Reports 02 and 03's exact commands were re-run from scratch.
- **Reports 01, 02, 03 (run_evaluation.py test-split results, and all 4 configurations in exp2_cost_accuracy.py): reproduced exactly** — precision/recall/F1/escalation-rate identical to 4 significant figures for `local_only`, `cloud_only`, `hybrid_static`, and `dual_tier` alike. These runs' own FAISS indexing evidently started from an empty or not-yet-corrupted file, so `_next_id` and `ntotal` happened to already agree throughout — the bug never triggered. **No changes needed to Reports 01, 02, or 03; their published numbers stand as originally reported.**
- **This report's exp3 threshold sweep: genuinely affected, and corrected above.** By the time exp3 ran, the shared index already held vectors from the preceding exp1/exp2 runs, so exp3's own `build_indexes()` call (which creates its own `FAISSIndex()` against that same shared path) hit the bug from its first added vector. The one cell where this mattered — τ_low=0.20/τ_high=0.70, the only cell with non-zero escalation — has been corrected from F1=0.222 to **F1=0.588 (P=1.000, R=0.417)**, re-measured against the fixed code with a clean index. The other 8 degenerate cells (0% escalation, Tier 1 only, no FAISS dependency) are unaffected and unchanged. The qualitative conclusion — that this experimental design produces a near-universal-peer-overlap corpus where Tier 1 alone dominates — is unchanged and, if anything, reinforced: even Tier 2's *corrected*, non-buggy behavior on this corpus (perfect precision, poor recall) still underperforms Tier 1 alone (F1=0.774).

**For Chapter 4/5:** this is a fourth genuine bug worth reporting alongside Report 01's two (Winnowing containment-gating, eval-harness fingerprint indexing) — all three fit the same pattern the thesis should describe honestly: DSR's "design as a search process" (Hevner et al. 2004) surfaced real defects only by actually running the system end-to-end and querying against the specific corpus/scenario each experiment demanded, not by code review or by trusting a component in isolation. See Report 06 for the full testing write-up this bug emerged from.

## Addendum 2 (2026-07-03): cross-submission indexing latency under concurrent load — investigated, a real bug found, and fixed

A natural follow-on question to Part C's single-submission latency demo: how long after student A submits does A actually become *checkable* by a subsequent submission B, and does that hold up when submissions arrive close together (the realistic case near an assignment deadline)? This was investigated directly against the live deployment rather than reasoned about abstractly.

### Architecture, as it actually is

Winnowing fingerprinting is indexed *synchronously*, as a side effect inside `tier1_detector.py`'s own `detect()` call (`fp_index.submit()`, line 54) — no gap. BM25 and FAISS indexing, however, happen in a separate, asynchronously-dispatched Celery task (`index_submission`, `backend/app/tasks/indexing_tasks.py`), fired via `.delay()` only after the detection task has already committed the submission as `COMPLETED`. Before this addendum's fix, the whole worker ran as a single process with `--pool=solo` (strictly one task at a time, across every queue: extraction, detection, embedding, indexing, ai_detection).

### First empirical test: 2 near-duplicate submissions, 438ms apart, both resolved correctly

Submitted via the live API directly (bypassing Moodle, to isolate backend queueing behavior from the cron layer Part C already covers). The second submission matched the first with a perfect score. Tracing the actual worker logs showed why: the single solo-pool worker fully drained submission A's entire task chain — extraction, detection, indexing, *and* AI-detection (the slowest single step, 156-575ms observed) — before it even started processing submission B's already-queued extraction task. So correctness held, but only as an accidental side effect of total serialization: the worker-side cost per submission was the sum of every step, including the one (AI-detection) that has nothing to do with cross-submission matching.

### The scalability problem this creates

Per-submission worker time, warm: extraction (~25ms) + detection (~27ms) + indexing (~41ms) + AI-detection (~150-575ms) ≈ 250ms-700ms, entirely serialized system-wide. Under a submission burst (many students near a deadline), the Nth submission's own detection cannot start until all N-1 prior submissions have *completely* finished processing — including their independent AI-detection step — not merely been accepted. This stacks linearly and was the mechanism behind `celery-worker` sitting at 89.9% CPU with a visible backlog during Report 06's 50-user Locust burst.

### Fix attempt 1 (wrong) and the bug it introduced

The first fix split the single worker into two: a serialized worker for `detection`+`indexing`, and a second, thread-concurrent worker (`--pool=threads --concurrency=2`) for `extraction`+`ai_detection`+`default` — reasoning that extraction and AI-detection touch only per-submission DB rows, never the shared Winnowing/BM25/FAISS state, so they're safe to parallelize.

Re-testing the same 2-submission race immediately surfaced a real regression: with extraction now concurrent, its *completion order* is what determines the order submissions are dispatched into the detection queue — and that order is no longer guaranteed to match submission order. In the test, the second submission's extraction happened to finish before the first's, so its detection ran against a corpus that didn't yet include the first submission at all, missing it entirely. The match was only caught from the other direction once the first submission's (delayed) detection ran later and found the now-indexed second one. This is a real, if partial, failure mode: the collusion pair *was* eventually discoverable (one of the two reports shows the link), but asymmetrically — whichever submission happened to finish extraction second is the one whose own report shows the flag, which does not necessarily match submission chronology, and a reviewer checking only the "first" submission's report in isolation would see nothing.

### Fix attempt 2 (correct): only AI-detection moves off the serialized worker

Extraction was moved back onto the same serialized worker as detection+indexing — since it's extraction's completion order that must track submission order, and extraction is cheap in the common case (~25-60ms for typical text), keeping it serialized doesn't reintroduce a real bottleneck. Only `ai_detection` (unambiguously independent: no ordering relationship to any other submission, never touches the shared indices, never gates `Submission.status`) moved to the concurrent worker. Deployed as two `docker-compose.yml` services: `celery-worker` (`--queues=extraction,detection,indexing,embedding --pool=solo`) and `celery-worker-fast` (`--queues=ai_detection,default --pool=threads --concurrency=2`, with `OMP_NUM_THREADS`/`MKL_NUM_THREADS` capped to 1 per thread to avoid oversubscribing the VM's 2 vCPUs on top of the added task-level concurrency).

**Re-verified against the same 2-submission race, then a 4-submission burst (2 duplicate pairs) for good measure:** both times, every submission resolved correctly in submission order — the earlier of each duplicate pair showed no match, the later one correctly matched it, with zero misses. Logs confirm the mechanism: the second submission's extraction now waits only on the first submission's *indexing* completing (the correctness-critical step, ~40-4000ms depending on cold-start state) — not on its AI-detection (which, observed directly, had already finished ~3.5 seconds earlier and caused no delay at all). Memory footprint with both workers running: ~1.1GB combined, well within the VM's real 7.8GB budget.

### For Chapter 4/5

This is worth reporting as a concrete instance of a broader, generalizable finding: naively parallelizing an async task pipeline built around shared, stateful indices can silently break the ordering guarantees that correctness depends on, even when no individual task is unsafe on its own (no crash, no exception, no corrupted data — just a quietly wrong answer for one specific ordering of two otherwise-correct operations). The fix that held up empirically was the conservative one: identify precisely which step in the chain the ordering guarantee actually depends on (dispatch order into detection+indexing, not everything downstream of it), and parallelize only what's provably independent of that (AI-detection). A more aggressive first attempt (parallelizing extraction too) looked reasonable on paper and was verified wrong by testing, not by inspection — the same DSR "design as a search process" pattern as the session's other four bugs.

## Addendum 3 (2026-07-04): Part A/B's entire "8/9 degenerate cells" finding was a sixth bug, not a corpus characteristic

While building a *different* script (`exp1b_threshold_resweep.py`, re-tuning thresholds against Report 02's corrected corpus after the dataset-leakage fix — see that report's own addendum), a re-run of the fixed sweep logic produced results inconsistent with the un-fixed version, which prompted checking this file's `exp3_threshold_sensitivity.py` for the same flaw. It had it.

### The bug

`Tier1Detector.detect()` calls `FingerprintIndex.submit()`, which **unconditionally inserts the queried document into the fingerprint index as a side effect** — documented in `winnowing.py` itself as "query first, then insert, for future queries." `run_experiment()` builds `tier1`/`tier2` **once**, then loops through 9 threshold configurations reusing those same objects (`for i, tl ... for j, th ... run_with_thresholds(tier1, tier2, submissions, tl, th)`). This means the *first* configuration's queries against the 38 test submissions insert every one of those submissions' own fingerprints into the index. From the *second* configuration onward, every test submission trivially matches **itself** (containment=1.0, exceeding any τ_high tested) — degenerating into "predict everyone plagiarised," which is exactly what the original F1=0.774 with ρ=0% pattern was: 24 of 38 test items are genuine positives, and 24/38 = 0.632 precision with recall=1.0 gives F1=0.774 — the signature of a trivial all-positive prediction, not a genuine corpus finding. The real-time demo section (5 repetitions with the same reused `tier1` object) had the identical flaw.

### The fix

Split index construction into two functions: `build_shared_indexes()` (BM25Index + FAISSIndex + Tier2Detector — genuinely safe to build once and reuse, since nothing in the sweep loop calls their mutating methods, only their read-only `search()`) and `build_fresh_tier1()` (a brand-new `FingerprintIndex`, re-seeded from only the genuine corpus, built fresh for every threshold configuration and every demo repetition). This is architecturally the same principle established in Report 02's addendum for the `exp1b` resweep script — cheap, stateless-per-trial components get rebuilt per trial; expensive, genuinely-shared components are built once.

### Why only *this specific pattern* (repeated sweeps over the same submissions) triggers it

`run_evaluation.py` (Reports 01-03) and `exp2_cost_accuracy.py`'s baselines were checked and do **not** have this bug — each processes every submission exactly once per script invocation, never re-querying the same submission under a second threshold configuration on the same object. The bug is specific to sweep-style scripts that intentionally re-run the same submission set multiple times against varying parameters while reusing detector objects — a pattern shared only by this file and the new `exp1b` script (both now fixed).

### Corrected findings, in full

Both the corrected Part A/B above (the real 9-cell grid, replacing the "8/9 degenerate" claim) and the corrected latency figures follow from this fix. The single non-degenerate cell already corrected earlier this session (Addendum 1, F1=0.222→0.588 for τ_low=0.20/τ_high=0.70) turns out to have been **coincidentally already correct** — it was the very first cell evaluated in the original iteration order, so it was never affected by the self-contamination bug (only cells 2-9 were). That earlier fix stands; everything else in the original Part A/B did not.

### For Chapter 4/5

This is a sixth genuine bug found this session (after the two in Report 01, the FAISS id_map bug in Reports 04/06, the celery-worker ordering bug above, and the dataset-leakage bug in Report 00/02/03/05), and arguably the most instructive for a methods discussion: it demonstrates that even a script whose *individual* logic was verified correct (Report 04's original text explicitly noted "this script's core gating logic was not a stale reimplementation... that part needed no fix" — true, in isolation) can still produce completely wrong aggregate results from how it's *driven* (reusing stateful objects across what should be independent trials). Verifying that each component call is individually correct is not sufficient; the harness orchestrating repeated calls needs the same scrutiny. This was caught only because a second, independently-written script doing conceptually the same thing (a threshold sweep) was cross-checked against it — worth noting as a concrete instance of why independent re-implementation/cross-validation of evaluation infrastructure has real value, not just of the system under test.

## Addendum 4 (2026-07-08): why cross-submission recall is actually poor — traced to the dataset, not just the detector

Part A/B's headline ("recall tops out at 0.417, a harder problem for this system than source-matching") is accurate but was under-explained — it reads as if the detector is simply worse at peer-matching. Investigating the actual corpus construction shows the real mechanism is more specific, and partially not about detector quality at all.

**The corpus is a merge of two differently-structured benchmarks**, confirmed via `labels.csv`'s `dataset` column: **Clough & Stevenson** (95 rows, `cs_*` filenames) — several students per task, all copying/paraphrasing *one shared* canonical reference answer (`source_ref=orig_task{a..e}.txt`) — and **PlagBench** (90 rows, `pb_*` filenames) — each sample has its own individually-named source file (e.g. `pb_source_verbatim_004.txt` belongs only to `pb_verbatim_004.txt`), not a source shared across multiple submissions.

Crucially, **the exp3 corpus is built from the train split of *submissions* only — it never includes `data/sources/`, the actual reference text each plagiarism sample was copied from.** So a test submission can only be caught if some *other* submission, independently derived from the same underlying material, happens to also be in the train split. Checking this directly against `labels.csv`/`splits/`:

```
Test-split submissions labeled is_plagiarised=1:                      24
...with a train-split submission sharing the exact same source_ref:   12
...with no such (source_ref-matching) partner at all:                 12
```

This "shared source_ref" check is a valid partner-detector for the Clough & Stevenson half (genuinely one shared source per task) but **undercounts** partners in the PlagBench half, since PlagBench assigns each sample a unique source filename even when several samples are independently derived from similar underlying content. This was confirmed directly, not assumed: re-running detection at the best config (τ_low=0.20, τ_high=0.70) and cross-referencing each test-positive's actual prediction against the partner check above gives:

| Bucket (by source_ref check) | Recall |
|---|---|
| Has a labeled partner (n=12) | **8/12 = 66.7%** |
| No labeled partner (n=12) | 2/12 = 16.7% (not zero — see below) |

The "no partner" bucket isn't actually zero, which is itself evidence the check undercounts: `pb_paraphrased_016.txt` (labeled "no partner") was correctly flagged, matching `pb_verbatim_007.txt` — a different PlagBench sample with an unrelated filename but genuine high similarity (dense=0.929, sparse/BM25=0.421, both real signals, not noise). `pb_verbatim_004.txt` similarly matched `pb_paraphrased_009.txt` (dense=0.902). Both are real cross-submission matches the naive source_ref check simply couldn't see coming.

**The second, independent mechanism — and the more actionable one:** of the 4 test-positives that *did* have a labeled partner but were still missed, all four scored in a narrow **0.600–0.651** band — just under `τ_high=0.70`:

| Submission | Score | τ_high |
|---|---|---|
| `cs_g0pA_taskd.txt` | 0.605 | 0.70 |
| `cs_g2pE_taskb.txt` | 0.600 | 0.70 |
| `cs_g3pB_taskd.txt` | 0.600 | 0.70 |
| `cs_g4pE_taskb.txt` | 0.651 | 0.70 |

These aren't cases where the detector found nothing — the score correctly rose in response to real overlapping content, it just didn't clear the source-matching-tuned bar. This looked, at the time, like it should be recoverable via a peer-matching-specific threshold retune with no new engineering — **Addendum 5 below actually ran that retune, and found this expectation was wrong**: lowering τ_high recovers some of these matches but simultaneously starts catching genuine false positives (same-topic, honestly-written "original" answers), so this is a real precision/recall tradeoff, not a free calibration fix. Read Addendum 5 before citing this paragraph's original optimism.

**For Chapter 4/5:** the honest, complete story is not "peer-matching is a harder problem for this system" as a single, flat statement — it's two separable effects, one addressable and one not: (1) a genuine, if smaller-than-naively-measured, corpus-coverage gap (some plagiarised test submissions truly have no matching content anywhere in the searched corpus, an artifact of this specific benchmark's construction, not a flaw in the detector) — not fixable by retuning; and (2) a threshold-calibration gap that Addendum 5 shows is real but *not free* — recovering it costs precision, because the same short-answer format that makes genuine copies detectable also makes independently-written same-topic answers score deceptively close to them. Reporting recall as a single 41.7% number without this breakdown understates the *complexity* of the gap, but Addendum 4's original claim that retuning "would recover a meaningful share... without new engineering" overstated how *free* closing it would be — see Addendum 5's actual sweep.

## Addendum 5 (2026-07-09): the peer-matching threshold retune was actually run — no free win, a real precision/recall tradeoff

Addendum 4 predicted that a peer-matching-specific `τ_high` (lower than the source-matching-tuned 0.68/0.70) would recover several of the near-miss genuine matches "without new engineering." This was tested directly with a wider sweep (`evaluation/experiments/exp3b_peer_threshold_resweep.py`, extending `τ_high` down to 0.50 in fine steps, same corpus/methodology as Part A/B), and the prediction was wrong in an important, specific way.

### The tradeoff, measured directly

| τ_high | Precision | Recall | F1 |
|---|---|---|---|
| 0.70/0.68 (deployed) | **1.000** | 0.417 | 0.588 |
| 0.65 | 0.917 | 0.458 | 0.611 |
| 0.62 | 0.800 | 0.500 | 0.615 |
| 0.60 | 0.722 | 0.542 | 0.619 |
| 0.55 | 0.722 | 0.542 | 0.619 |
| 0.50 | 0.64–0.75 | 0.625–0.667 | 0.65–0.68 |

(Full 30-cell grid across τ_low ∈ {0.20, 0.25, 0.30} × τ_high ∈ {0.50...0.80}: `evaluation/reports/raw/04_exp3b_peer_resweep_results.json`.)

**Precision holds at a perfect 1.000 all the way down to and including 0.68 — then drops the instant τ_high crosses below 0.65, and keeps eroding as τ_high falls further.** This is not threshold noise: the specific new false positive at τ_high=0.65 was identified directly — `cs_g0pB_taskb.txt`, labeled `category=original` (i.e. genuinely **not** plagiarised), scores 0.679, just past the lowered bar. It is a Clough & Stevenson task-b answer that happens to use similar technical vocabulary to other task-b submissions purely because it's independently, honestly answering the same question — exactly the "topical convergence" failure mode named as a risk in the original in-depth discussion of this limitation, now directly confirmed with a concrete example rather than left as a theory.

### What this means

A real F1 improvement is available (0.588 → ~0.62 by τ_high≈0.60, or higher still at 0.50) — but only by giving up the "never a false accusation" property this system has held at every previously-tested peer-matching configuration. For an academic-integrity tool, a false positive has a real cost (a student wrongly flagged), arguably a worse failure mode than a missed detection in this domain (which a human reviewer can still catch through normal grading). **The deployed `τ_high=0.68` is not a source-matching-only compromise being carelessly reused for peer-matching — it is very close to Pareto-optimal for peer-matching too**, if "never falsely accuse" is treated as close to a hard constraint rather than one factor to trade off. This reverses Addendum 4's framing: the gap wasn't sitting there uncalibrated waiting to be picked up "for free" — the calibration is *already* near-optimal for a zero-false-positive operating point on this specific corpus.

**Caveat on statistical confidence:** the test split here is small (38 items, 24 positive) — a single misclassified item swings precision or recall by 3–7 percentage points. The *direction and existence* of the tradeoff (precision drops sharply once τ_high crosses ~0.65-0.68, driven by same-topic non-plagiarism answers) is a real, mechanistically-explained finding, not noise — but the exact F1/precision values at each cell should be read as indicative, not as precise operating-point recommendations, given the sample size.

**For Chapter 4/5:** this is a genuinely useful negative result, and a stronger methodological story than "we retuned it and improved recall" would have been — it demonstrates the DSR "search process" surfacing a real design constraint (precision/recall tradeoff, driven by a specific, named confound in the underlying benchmark) rather than a bug, and shows the deployed threshold was already a reasonable choice rather than an oversight. Worth reporting alongside Addendum 4 as a complete two-part story: first the honest diagnosis of *why* recall looked poor (corpus coverage + apparent miscalibration), then the honest test of the "obvious fix," which showed the miscalibration framing was itself incomplete — a valuable, if humbling, second-order finding.

**Pointer, not a validated result:** since a threshold-only fix has a real precision cost, `evaluation/experiments/prototype_skeleton_feature.py` (2026-07-09) is a feasibility spike testing whether a second, structural signal — Stamatatos (2011) stopword-n-gram "skeleton" overlap, which strips content words and compares only function-word sequence structure — can separate genuine copies from same-topic-only answers in exactly this score band, without a precision cost. Preliminary result: requiring `skeleton_containment ≥ 0.25` alongside a lowered `τ_high=0.60` recovers real recall (0.375→0.500 in this script's own consistent scoring) while keeping precision at 1.000, correctly rejecting the exact false positive (`cs_g0pB_taskb.txt`) found above. This is a feasibility signal only — not integrated into the real gating pipeline, not re-validated at Reports 01-06's rigor bar, and built on a cruder whole-document version of the technique rather than Stamatatos's original sentence-bounded method. Read the script's own docstring for full caveats before citing this as more than "worth pursuing."

## Addendum 6 (2026-07-09/10): the structural signal, built for real — a genuine peer-matching win, and an honest source-matching failure that stopped it from shipping enabled

The prototype was built properly into the live pipeline (not left as a spike) and validated against **both** corpora, as Addendum 5's own methodology demanded. The result is a real, useful positive finding on one corpus and a real, instructive negative finding on the other — and the final shipped configuration reflects the negative finding, not the positive one, because this system's one non-negotiable property (per Addendum 5) is never trading away precision.

### What was built

`backend/app/services/structural_detector.py` (new): `skeleton_ngrams()`/`skeleton_containment()` (asymmetric containment, matching this codebase's established convention from `winnowing.py`), and `sentence_skeleton_score(text_a, text_b)` — splits both texts into sentences (via a small refactor: `embedding_service.py`'s inline sentence-split regex was hoisted into a shared `split_sentences()` helper, zero behavior change to `chunk_text()`, confirmed by its existing tests staying green) and returns the best-scoring sentence pair, mirroring `Tier2Detector`'s own "best chunk pair wins" pattern. Wired into `detection_pipeline.py`'s `run_detection()`: when an escalated submission's Tier 2 score falls short of `TAU_HIGH` but lands in `[STRUCTURAL_TAU_VERIFY, TAU_HIGH]` (a "suspicious but not auto-confirmed" band), `maybe_structural_confirm()` runs the check against the real matched document's text (via `BM25Index.get_text()`, the only existing DB-free doc_id→text lookup) and can flip `is_plagiarised` from False to True. New `PipelineResult` fields `structural_score`/`structural_confirmed` for transparency. Fully gated behind `settings.STRUCTURAL_ENABLED` (kill-switch, verified by a dedicated test that behavior is byte-identical to pre-feature when off). 35 new/extended unit tests (`test_structural_detector.py`, `test_pipeline.py`'s new `TestStructuralConfirmation` class); full suite 132/132 passing.

### First real-pipeline bug, caught by testing: short sentences produce spurious perfect matches

The very first real-pipeline peer-matching run (`evaluation/experiments/exp4_structural_signal_validation.py`, real `run_detection()` through the actual singletons, not the prototype's approximated always-escalate methodology) at the prototype's own `STRUCTURAL_SKELETON_THRESHOLD=0.25` confirmed 7 items — only 3 were genuine copies; 4 were the same kind of "original"-category false positive the feature was built to prevent, including one scoring a **perfect 1.0** skeleton containment. Diagnosed directly (not guessed): all 4 were driven by short (5-14 word) sentences — e.g. `"Design technique, like divide-and-conquer method."` (5 words) coincidentally sharing a 4-gram function-word skeleton with an unrelated sentence elsewhere, purely because a short sentence has so few n-grams that one coincidental match dominates the containment ratio. All 3 genuine recoveries, by contrast, came from 16-31 word sentences on both sides. Fixed with a `MIN_SENTENCE_WORDS=15` filter (a general, evidence-grounded statistical fix — not tuned tighter than the diagnosed gap between 5-14 words and 16-31 words) plus raising `STRUCTURAL_SKELETON_THRESHOLD` to 0.30. Re-verified: **peer-matching precision returned to a perfect 1.000, recall improved from 0.417 to 0.542 (F1 0.588→0.703)**, confirming exactly the 3 genuine copies with zero false positives (`evaluation/reports/raw/04_exp4_structural_validation_peer_results.csv`).

### The critical check Addendum 5 required — and a real, deeper problem it found

Per this session's own established rule ("if source-matching regresses... not shipping regardless"), the fixed configuration was then run against the **source-matching** corpus (`python -m evaluation.run_evaluation --split test`, Reports 01-03's methodology — zero script changes needed since it already calls the real `run_detection()`). Result: **precision dropped from the documented 1.000 to 0.885** (3 new false positives), even with the same fix that had just cleanly solved the peer-matching case.

Diagnosed directly: all 3 were same-task "original" submissions independently defining a canonical technical concept — Bayes' Theorem, PageRank, dynamic programming — using standard textbook-style phrasing that a *second* independent writer also converges on, purely because there's essentially one conventional way to state the definition. This is the exact "canonical-definition convergence" confound already documented in Report 05, now shown to affect the *structural* signal too, not just the lexical/embedding ones. The deeper, more general mechanism: **source documents are longer and have far more candidate sentences than peer submissions** (source texts here: 18-20 sentences ≥15 words; peer submissions: 4-9) — a "max over all sentence pairs" comparison is a multiple-comparisons problem, and more candidate pairs means a higher chance that *some* pair coincidentally clears any given threshold, independent of any genuine relationship.

A refinement was attempted before giving up: requiring the **top-2** best-scoring pairs to both clear the threshold (corroboration, not a single coincidental hit). It did not cleanly work either — checked directly, the false positives' second-best scores (0.267-0.385) and the genuine recoveries' second-best scores (0.333-0.444) **genuinely overlap** on this dataset; no single threshold on any aggregation tested separates both corpora cleanly. This was not treated as a reason to keep tuning further — see below.

### Decision: ship built, tested, and disabled by default

`STRUCTURAL_ENABLED` defaults to **`False`**. The feature is fully implemented, fully tested (including the specific real false-positive/true-positive cases from both corpora as pinned regression fixtures), and available as an opt-in — but production behavior is unchanged from before this work, confirmed by re-running the source-matching regression check with the default restored: precision back to exactly 1.000, F1 back to exactly 0.884, byte-identical to Reports 02/03's numbers (`evaluation/reports/raw/04_exp4_structural_validation_source_regression_check.csv`).

**For Chapter 4/5:** this is a complete, honest DSR "build-evaluate" cycle, and arguably a better methods story than shipping the feature would have been: a literature-grounded technique (Stamatatos 2011) was implemented properly, found a real, measurable win on a first, narrower validation (peer-matching: +12.5 points of recall at no precision cost), and was then subjected to the broader validation this project's own established discipline required — which caught a real, mechanistically-understood failure mode (the multiple-comparisons problem in longer documents) that the narrower validation could never have revealed. The fix that would have "worked" locally (lowering the bar further, or the top-2 refinement) was rejected specifically because it was verified, not assumed, to also let through more false positives elsewhere. This fits the exact same pattern as every other real bug this session found: the first fix that looks right on a narrow check is not automatically right everywhere it will run, and only running the broader check — not reasoning about it harder — reveals the gap. **Legitimate future work, not attempted here**: anchoring the structural comparison to the *specific chunk* Tier 2 already flagged as the best match (rather than searching every sentence pair in the whole document) would directly remove the multiple-comparisons problem at its root, since it stops the comparison from ever seeing the other 15-40 unrelated sentence pairs in a long source document; this would need `Tier2Detector` to expose which chunk (not just which document) it matched, which it does not currently do.

## Addendum 7 (2026-07-11): the chunk-anchoring fix was built — real progress, still not enough to ship enabled

Addendum 6's named future work was built: `Tier2Detector.detect()` now tracks, alongside its existing document-level fusion, exactly which submission chunk and which source chunk (by index) produced the winning dense score (`Tier2Result.best_submission_chunk`/`best_source_chunk_index`), recovered without touching the fusion math itself — a parallel dict updated in lockstep with the existing `dense_scores[base_id] = max(...)` line. The structural-confirmation call site in `detection_pipeline.py` now passes the specific matched *chunk* pair's text instead of the whole submission/source documents. (This same chunk-exposure change also enabled a second, independent feature — real match explanations, `SimilarityPair.matched_segments` — see the accompanying implementation notes; that feature ships regardless of this addendum's outcome, since it doesn't depend on `STRUCTURAL_ENABLED`.)

### Re-validated against both corpora, same discipline as Addendum 6

**Peer-matching: unchanged, the win holds exactly.** `evaluation/experiments/exp4_structural_signal_validation.py` re-run with chunk-anchoring: **P=1.000, R=0.542, F1=0.703** — identical to Addendum 6's whole-document numbers. Expected: peer submissions in this corpus are short enough that they're typically a single chunk, so "chunk-anchored" and "whole-document" comparison collapse to the same thing for most of this corpus.

**Source-matching: real improvement, not a full fix.** `python -m evaluation.run_evaluation --split test` with `STRUCTURAL_ENABLED=True` and chunk-anchoring: **precision 0.885→0.920** (2 false positives, down from 3 — `cs_g3pC_taskb.txt` is now correctly rejected). But **not** the ~1.000 needed to safely ship enabled. The 2 remaining false positives are the same two hardest cases from Addendum 6 (`cs_g4pE_taske.txt` matching `orig_taske.txt`'s dynamic-programming passage; `cs_g0pB_taskb.txt` matching `orig_taskb.txt`'s PageRank passage) — both same-task "original" answers independently restating a canonical technical definition. Diagnosis: a `chunk_text()` chunk defaults to up to 256 words, which can still contain several qualifying (≥15-word) sentences — chunk-anchoring shrinks the multiple-comparisons search space from "every sentence in the whole document" to "every sentence in one ~256-word chunk," which measurably helps, but doesn't shrink it to zero. These two cases' canonical-definition sentences happen to land in the same winning chunk pair as their genuine dense-similarity match, so the structural check still sees enough candidate sentence pairs within that one chunk to occasionally clear the bar by chance.

### Decision: still ships disabled by default

`STRUCTURAL_ENABLED` stays **`False`**. 0.920 is a real, meaningful improvement over 0.885, but this system has held a perfect zero-false-positive record on source-matching at every configuration tested across Reports 02/03/04 — that bar doesn't relax for a partial win. The chunk-anchoring code ships (it's a genuine improvement, fully tested, and required for match explanations regardless), but the feature flag stays off pending a fix that actually closes the remaining gap, not just narrows it.

**For Chapter 4/5:** a second honest, complete iteration of the same DSR cycle — the proposed fix from Addendum 6 was built and it *worked*, partially, exactly as diagnosed (fewer candidate sentence pairs → fewer coincidental matches → higher precision), which is itself a confirmation that the multiple-comparisons diagnosis was correct, not just plausible. But "partially fixed, mechanistically as predicted" is still not "fixed enough to ship," and the honest report is the second, not the first. **Remaining future work, more precisely scoped now**: true sentence-pair anchoring (not just chunk anchoring) — using the *specific* matched sentence pair Tier 2's dense retrieval identified, rather than the whole chunk containing it — would shrink the comparison further still, but FAISS is currently indexed at chunk granularity only; reaching sentence granularity would need re-indexing at a finer level, a materially bigger change than this pass's, and not attempted here.
