# Report 7: Full Pipeline Audit (End-to-End)

**Status:** Audit done, all 5 main findings + both lower-severity findings patched and deployed (2026-07-04) — see "Fixes applied" section below. **Two further findings closed later**: Finding 2's remaining FAISS dangling-reference gap (2026-07-08 follow-up) and a ninth finding — match explanations were fully-built, silently-dead infrastructure since inception (2026-07-11 follow-up, near the end of this file).
**Roadmap step:** Not in the original roadmap — requested directly after the session's run of real bugs (Reports 00-06) prompted a full, deliberate audit rather than continuing to find issues incidentally.
**Scope:** Every layer of the system read and traced by hand: evaluation metrics/statistics, Tier 1/Tier 2 detection services, the Celery task chain, the FastAPI layer, the database models, and the Moodle plugin (observer, API client, report page, capability definitions). Config reviewed for stale defaults.

## Method

Given how many of this session's bugs were "the individually-correct-looking code was wrong in how it was *driven* or *composed*" (shared mutable state reused across calls, corpus construction, threshold calibration drift), this audit specifically looked for the same *classes* of issue — silent side effects, unvalidated cross-references between independently-supplied identifiers, dead/superseded code creating false confidence, and missing bounds/timeouts — rather than re-deriving whether each file's own internal logic was self-consistent (already covered file-by-file in Reports 00-06 for the components those reports touched).

## Findings, most significant first

### 1. `report.php` — cross-course/cross-module report disclosure (IDOR), no dedicated CVSS but a real confidentiality issue

`moodle-plugin/plagiarism/dualtier/report.php` authorizes the request against `$cmid` (`require_capability('plagiarism/dualtier:viewreport', $context)`, where `$context` is built from `$cmid`), but then fetches the actual report **by `$id` alone** (`$DB->get_record('plagiarism_dualtier_files', ['id' => $id], ...)`) with no check that `$record->cmid === $cmid`. `$id` and `$cmid` are both independently-supplied, unrelated URL parameters.

**Impact:** `viewreport` is granted to `teacher`/`editingteacher`/`manager` archetypes (`db/access.php`) — not students by default, so this isn't directly student-exploitable — but a teacher with `viewreport` in *any single* module they teach can view *any other* module's plagiarism report (any course, any student, anywhere in the Moodle instance) by supplying that one authorized `cmid` alongside an arbitrary `id`. This is a genuine cross-course/cross-teacher data disclosure of sensitive academic-integrity records.

**Fix:** immediately after fetching `$record`, verify `(int) $record->cmid === $cmid`, and `throw new moodle_exception('invalidrecord', ...)` (or similar) if not. One line, no design change needed.

### 2. Winnowing/BM25/FAISS indices are never purged when a submission is deleted

`DELETE /api/v1/submissions/{id}` (`backend/app/api/v1/submissions.py`) deletes the `Submission` row, which correctly cascades to `Document`/`DetectionResult`/`SimilarityPair` at the database level (`cascade="all, delete-orphan"` in the ORM relationships, confirmed in `models/submission.py` and `models/result.py` — `SimilarityPair.source_document_id` uses `ondelete="SET NULL"` so it doesn't leave a dangling FK either). **But nothing in this code path calls `FingerprintIndex.remove()`, `BM25Index.remove()`, or removes the corresponding FAISS vectors.** The in-memory detection indices are entirely separate from the database and are never told a submission was deleted.

**Impact:** a "deleted" submission's content remains permanently discoverable and matchable by future submissions — the database says it's gone, but the detection system still has it fully indexed. For a system whose stated purpose includes "cross-submission checks," this is a real gap, and plausibly also relevant to any data-subject-erasure expectations (the plugin's own `privacy/provider.php` documents what's stored, which implies some expectation of being able to actually remove it).

**Fix:** `delete_submission()` should look up the submission's document IDs before deleting and call `fp_index.remove(doc_id)` / `bm25_index.remove(doc_id)` for each — FAISS doesn't currently expose a per-vector remove (only whole-index rebuild), which is a smaller, separate gap worth noting for future work (removing a single vector from `IndexFlatIP` isn't natively supported without rebuilding).

### 3. `observer.php` — the "dedup" identifier field is computed and stored, but never actually checked

`plagiarism_dualtier_files.identifier` is documented (`db/install.xml`: "Content hash (SHA-256)", `privacy/provider.php`: "A hash of the file content") and computed correctly in `observer.php` (`hash('sha256', $plaintext)` for online text; `$file->get_contenthash()` for files) — but grepping the entire plugin confirms it is **never read back or compared against anywhere**. `queue_submission()` unconditionally inserts a new tracking record and queues a new `submit_file` ad-hoc task on every `file_uploaded` event, with no check for an existing record with the same `cmid`+`userid`+`identifier`.

**Impact:** Moodle is known to sometimes fire `assessable_uploaded` more than once for a single logical submission action. Each firing here creates an independent tracking record and an independent backend submission — wasted Tier 2 cost if either escalates, redundant fingerprint/BM25/FAISS index entries under different synthetic doc_ids for identical content, and (via `lib.php`'s `get_links()`, which picks the single most-recently-modified record for a cmid+userid pair) a real risk of the displayed badge/score flipping between near-duplicate submissions' independently-computed results if their completion times interleave.

**Fix:** before inserting in `queue_submission()`, check for an existing `plagiarism_dualtier_files` record with the same `cmid`, `userid`, and `identifier`; if found and not in an error state, skip re-queueing.

### 4. `api_client.php` — no timeout on `submit_file`/`get_status`/`get_results`, inconsistent with `is_healthy()`

`is_healthy()` explicitly sets `CURLOPT_CONNECTTIMEOUT`/`CURLOPT_TIMEOUT` (5s/10s). The three calls that actually matter for correctness under load — `submit_file()`, `get_status()`, `get_results()` — set no timeout at all, relying on whatever Moodle's `\curl` class defaults to.

**Impact:** if the backend ever hangs or becomes slow (overloaded worker, network blip), these calls could block for an extended, unbounded period. This is more consequential now than when originally written, since `poll_result.php` (added 2026-07-04, see Report 04's Part C follow-up) calls `get_status()` from a task that's meant to complete quickly and re-queue itself every 15 seconds — a hung call here would stall that specific cron.php invocation and delay every other task scheduled to run in the same pass.

**Fix:** add the same `CURLOPT_CONNECTTIMEOUT`/`CURLOPT_TIMEOUT` pattern already used in `is_healthy()` to the other three methods (a slightly longer timeout than the health check is reasonable for `submit_file`, since a real detection call is heavier than a liveness ping).

### 5. `index_document()`'s periodic FAISS save can silently skip its own trigger point

```python
if faiss_idx.total_vectors % 100 == 0 and faiss_idx.total_vectors > 0:
    faiss_idx.save()
```
(`backend/app/services/detection_pipeline.py`). A single call to `index_document()` can add more than one vector at once (a multi-chunk document via `tier2.index_chunks()` → `FAISSIndex.add_batch()`). If the vector count jumps from, say, 98 to 102 in one call, it never equals a multiple of 100, and the save is skipped — not deferred to "next time," but skipped for however long it takes the count to *happen* to land exactly on a future multiple of 100 again, which depends on the (variable, content-dependent) chunk count of each subsequent document.

**Impact:** a durability/data-loss-window issue, not a correctness-of-computation one — the FAISS index (and, since 2026-07-04, its `.meta.json` doc_id-mapping sidecar) can go far longer than the intended "every 100 vectors" between persisted saves, widening the window of vectors that would be lost on an unclean shutdown before the *next* fix (Report 04/06's `_next_id`/meta-persistence fix) can even do its job on restart.

**Fix:** compare "which hundred-bucket was I in before this add vs. after" (`before // 100 != after // 100`) instead of exact-equality, or simply save unconditionally every call to `index_document()` if save() is cheap enough (it's a single `faiss.write_index()` + small JSON dump — likely acceptable given the escalation rates measured in Reports 02/03 are well under 100% of submissions).

## Findings, lower severity / code-quality

### 6. `bm25_service.py`'s `robust_min_max_normalize()` is dead code with its own passing unit tests

Defined, documented, and unit-tested in `test_bm25.py` — but `BM25Index.search()` uses an inline proportional-normalization calculation instead (`raw_scores / saturation_score`, clipped) and never calls this function. Not a behavioral bug (unused code can't produce a wrong answer), but exactly the kind of "tests pass, therefore it must be in use" false confidence that has repeatedly mattered this session (see the `generate_embeddings` dead-code task found on 2026-07-03, same pattern). Worth removing, or wiring in a comment at the top of `search()` explicitly noting `robust_min_max_normalize()` was the earlier approach and is intentionally superseded, so a future reader doesn't wonder which one is live.

### 7. The sentence-embedding model is never explicitly preloaded, unlike the AI-detector model

`celery_app.py`'s `_preload_detection_services()` (the `worker_ready` signal handler) constructs `Tier1Detector`/`Tier2Detector` objects and explicitly warms the AI-detector model (`_get_ai_model()`) — but `Tier2Detector.__init__` never touches `embedding_service.get_model()`, and nothing else calls `encode_texts()` at startup either. The sentence-transformer model (`all-MiniLM-L6-v2`) is therefore still fully lazy-loaded on whichever request happens to be the first real Tier 2 call or indexing call after a fresh worker start.

**Impact:** this is the concrete, previously-unexplained cause of the multi-second "cold start" latency spikes observed earlier this session (an `index_submission` task that took 4.16s and an `extract_text` task that took 3.5s, both immediately after a fresh container start, both left unexplained at the time as "likely a cold-start effect"). It also leaves a latent thread-safety gap in `embedding_service.get_model()`'s lazy-singleton pattern (no lock around the `if _model is None` check) — currently not exploitable because the detection worker runs `--pool=solo` (single-threaded), but it would become a real race if anyone ever increases that worker's concurrency without also addressing this (a mistake this exact audit is meant to make less likely).

**Fix:** add a warmup call (`encode_texts(["warmup"])`) to `_preload_detection_services()`, matching the pattern already used for the AI-detector model.

### 8. File-upload size validation happens after the full file is read into memory

`create_submission()` (`submissions.py`) does `content = await file.read()` (unbounded) and only checks `len(content) > max_bytes` afterward. This doesn't prevent a large upload from being fully buffered in memory before rejection — it only rejects it after the fact. Likely already bounded in practice by an upstream reverse-proxy/ASGI-server body-size limit (not verified as part of this audit, since that configuration lives outside this repo), but worth confirming explicitly rather than assuming, and streaming/size-checking incrementally would be the more defensible implementation regardless.

## Fixes applied (2026-07-04, same day)

All 5 main findings and both lower-severity findings were patched, deployed, and re-verified rather than left as documented-only:

- **Finding 1 (`report.php` IDOR):** fixed with a single cross-check (`if ((int) $record->cmid !== $cmid) throw ...`) immediately after fetching the record. PHP syntax-validated (`php -l`); not live-tested end-to-end (would require simulating two separate course modules and two teacher accounts, judged out of proportion to the one-line fix).
- **Finding 2 (index purge on delete): fixed, but the first attempt was itself wrong, and testing caught it, not review.** The first patch called `get_fingerprint_index().remove(...)`/`get_bm25_index().remove(...)` directly inside the FastAPI `delete_submission()` route handler. Live-testing it (submit two duplicates, confirm they match, delete both, submit a fresh duplicate, expect no match) showed the fresh duplicate *still* matched — the fix had done nothing. Root cause: `get_fingerprint_index()`/`get_bm25_index()` are per-*process* singletons with no IPC; the real, populated indices live in the `celery-worker` container's process, not the `api` container's. Calling `.remove()` from the API route mutated an unused, separate copy. **Corrected fix:** a new Celery task (`app/tasks/purge_tasks.py::purge_documents`, routed to the `indexing` queue — the same serialized worker that owns this shared state) is dispatched via `.delay()` from `delete_submission()` instead of calling `.remove()` in-process. Re-tested with the same methodology: confirmed the purge task now runs in the celery-worker process (`documents_purged` logged there), and a fresh duplicate submitted after deletion correctly shows `tier1_score=0.0, matches=[]`. FAISS vectors remain unpurged (documented limitation, unchanged).
- **Finding 3 (`observer.php` dedup):** fixed — `queue_submission()` now checks for an existing non-error record with the same `cmid`+`userid`+`identifier` before inserting, and returns early if found. PHP syntax-validated; not live-tested (would require triggering Moodle's `assessable_uploaded` event twice for one submission, which isn't reliably reproducible from outside Moodle's own internals).
- **Finding 4 (`api_client.php` timeouts):** fixed — added `CURLOPT_CONNECTTIMEOUT`/`CURLOPT_TIMEOUT` to `submit_file()`, `get_status()`, and `get_results()` (30s/15s/15s respectively, `submit_file` longer since a real upload is heavier than a status poll). PHP syntax-validated.
- **Finding 5 (unreliable FAISS save trigger):** fixed — `index_document()` now captures `total_vectors` before and after the add and compares `before // 100 != after // 100` (bucket comparison) instead of exact-equality-to-a-multiple-of-100. Covered by the existing test suite's `test_pipeline.py`/`test_tier2.py` runs (94→89 after finding 6's cleanup, still 100% passing).
- **Finding 6 (dead code):** `robust_min_max_normalize()` and its 5 dedicated unit tests removed entirely from `bm25_service.py`/`test_bm25.py`. Also cleaned up two other pre-existing unused imports found in the same file while there (`string`, `defaultdict`) and a stale type hint (`self._index: BM25Okapi | None` — `BM25Okapi` was never imported; only `BM25Plus` is actually used) that was silently inert only because of `from __future__ import annotations`.
- **Finding 7 (embedding model not preloaded):** fixed — `_preload_detection_services()` now calls `encode_texts(["warmup"])` after constructing the Tier 1/Tier 2 detectors. Verified directly in worker startup logs: `loading_model`/`model_loaded` for `all-MiniLM-L6-v2` now appear during the `preloading_detection_services` phase, before `detection_services_preloaded` — confirmed no longer deferred to the first real submission.
- **Finding 8 (unbounded upload read):** not fixed this pass — flagged as lower priority (likely already bounded upstream by nginx/uvicorn, unverified) and a larger change (streaming size-check) than the others; left as a documented, open item.

Full test suite re-run after all Python changes: **89/89 passing** (94 minus the 5 removed dead-code tests), coverage unaffected in any meaningful way.

## For Chapter 4/5

This report and its fixes are worth reporting as a single, complete narrative arc, not just a list of bugs: a systematic, adversarial audit pass — looking specifically for the *shape* of defect this project had already demonstrated it was prone to (shared state, unchecked cross-references, dead-but-tested code, missing bounds) — found 7 real, previously-unknown issues in components that had not yet been individually scrutinized, none caught by the existing unit test suite because none are unit-testable in isolation the way the earlier bugs were. Then, patching finding 2 produced a *second*, self-contained instance of the exact same lesson this whole session keeps demonstrating: the first fix looked correct on inspection (right index, right method, right doc_ids) and was still completely wrong, because it didn't account for process boundaries — caught only by re-running the same live verification test used to justify writing the fix in the first place, not by re-reading the code more carefully. This is arguably the single clearest illustration in the whole thesis of why DSR's "design as a search process" (Hevner et al. 2004) framing matters: even a careful, deliberate, adversarial-minded audit pass produced a wrong fix on the first attempt, and only empirical re-verification — not more careful reasoning — caught it.

## Follow-up (2026-07-08): Finding 2's remaining FAISS gap closed — and a sharper problem found first

Finding 2's fix (above) explicitly left FAISS vectors unpurged, framed as a smaller, separate limitation ("removing a single vector from `IndexFlatIP` isn't natively supported without rebuilding"). Revisiting this while writing `docs/USER_GUIDE.md` (2026-07-07/08) turned up something worse than "unpurged": because `purge_documents` never touched `FAISSIndex._id_map`/`_doc_map`, and `search()` resolves every hit back to a doc_id with **no existence check at all**, a deleted submission's dense vector wasn't just inert — it was **actively returned as a live match candidate indefinitely**, carrying a doc_id with no backing database row. A dangling-reference correctness bug, not just wasted compute.

**Fix:** migrated `FAISSIndex` (`backend/app/services/faiss_service.py`) from raw `IndexFlatIP`/`IndexIVFPQ` to both wrapped in `faiss.IndexIDMap2`, which supports real `remove_ids()`. New `remove_document(doc_id)` method, chunk-aware (a submission's base doc_id fans out into `f"{doc_id}__chunk_N"` FAISS keys via `tier2_detector.index_chunks()` — a caller only supplying the base doc_id needs prefix-matching removal, not exact-key, or every chunk's vector would silently survive). `purge_documents` now calls it alongside the existing Winnowing/BM25 removal. Legacy (pre-this-change) persisted index files are migrated to the new format automatically, in-memory, the first time they're loaded — no separate offline migration script or manual VM data surgery needed.

**This fix was itself only correct after three rounds of empirical testing against the real installed `faiss-cpu` package, not on the first attempt** — consistent with the pattern this whole report already documents (finding 2's own first fix attempt was also wrong until live-tested):
1. A first design (wrap an already-populated legacy index directly in `IndexIDMap2`) failed immediately: FAISS hard-rejects this (`index must be empty on input`) — not a corner case, a guaranteed crash on every legacy file, caught only by actually running it, not by reading FAISS's Python API surface.
2. The corrected design (`reset()` the legacy index to clear vectors while preserving training, wrap the now-empty index, `add_with_ids()` the reconstructed vectors back in) worked correctly for the Flat backend — confirmed by direct testing (add/search/remove/reload round-trips all correct).
3. The same pattern applied to the IVFPQ backend (used only past ~1,000 vectors, via `upgrade_to_ivfpq()` — itself confirmed unreachable dead code in the live deployment, no caller exists) surfaced a third, more serious problem: `remove_ids()` on an IVF-family index wrapped in `IndexIDMap2` **partially mutated the index — dropping most of its searchable contents — before raising an exception**, not a clean no-op failure. This is a real, confirmed FAISS behavior specific to this backend combination, not a hypothetical edge case. Because IVFPQ is unreachable in production today, the fix does not attempt to make IVFPQ removal work; instead `remove_document()` detects an IVF-backed index up front (via `faiss.downcast_index()` + `isinstance(..., faiss.IndexIVF)`) and refuses before calling `remove_ids()` at all, logging a warning rather than risking corruption. Add/search still work correctly for IVFPQ (tested), only removal is guarded off.

**Verification:** 14 new/extended unit tests (`backend/tests/test_faiss_service.py`, `backend/tests/test_purge_tasks.py`) — all passing — including a direct test of the actual bug being fixed (search a removed doc_id's own former vector, assert it's never returned) and a direct test that the IVFPQ guard refuses cleanly (index left fully intact, not partially corrupted) rather than crashing. Full detailed design record: `docs/2026-07-08/faiss_vector_removal_1223.md`.

**For Chapter 4/5:** an eighth genuine bug this session, found by re-reading code while documenting a "known limitation" rather than treating the limitation as settled — and its fix needed the same empirical-validation discipline as finding 2's own correction, including one discovery (the IVF partial-mutation-before-raising behavior) that would have been very easy to miss with unit tests alone if IVFPQ had a live production path, since the failure mode isn't "throws an error" but "throws an error *after* silently damaging state," which a test asserting only `pytest.raises(...)` would not have caught without also asserting post-failure state integrity.

## Follow-up (2026-07-11): a ninth finding — match explanations were dead infrastructure since inception, closed while building a different feature

While investigating what the structural-signal fix (Report 04's Addendum 7) would need to anchor its comparison to a specific matched chunk, it became clear that a complete, real feature's *display* infrastructure already existed and had **never been wired up**: `backend/app/models/result.py`'s `SimilarityPair.matched_segments` (a JSONB column), `backend/app/schemas/result.py`'s `MatchedSegment` schema, and `moodle-plugin/plagiarism/dualtier/report.php`'s rendering loop (lines 99-113, iterating `$match->matched_segments`, rendering submitted/source text side-by-side) all existed, fully consistent with each other — but nothing anywhere in the detection pipeline (`detection_tasks.py`, `tier2_detector.py`, `detection_pipeline.py`) ever wrote a value into that column. Every submission's report page had silently rendered an empty matched-passages section, for every submission, since this schema/UI was first built — the same *shape* of finding as this report's other 8 (a feature that looks complete end-to-end but has a silent gap that only shows up by tracing the real data flow, not by reading any one file in isolation), just never previously audited because it wasn't flagged as a "known limitation" the way finding 2's FAISS-purge gap was.

**Fix:** `Tier2Detector.detect()` (`backend/app/services/tier2_detector.py`) now tracks, alongside its existing document-level score fusion, exactly which submission chunk and which source chunk index produced the winning dense score (`Tier2Result.best_submission_chunk`/`best_source_chunk_index`) — a parallel dict updated in lockstep with the existing `dense_scores[base_id] = max(...)` line, not a restructure of the fusion math itself. New `backend/app/services/segment_extraction.py` (`extract_matched_segment()`) recovers the actual matched text and character offsets from that chunk pair, re-chunking the source document's text via the same deterministic `chunk_text()` used at index time. Wired through `detection_pipeline.py` → `detection_tasks.py`'s existing `SimilarityPair` construction.

**Scope, deliberately bounded:** match explanations only work for Tier-2-resolved (escalated) detections. Tier 1 (Winnowing) was confirmed, not assumed, to be structurally incapable of supporting this without materially larger new instrumentation: `FingerprintIndex.submit()` discards positional information immediately (`hash_values = {h for h, _ in fp}`, keeping only hash values), and even if positions were kept, they index into the post-`preprocess()` stripped string, which isn't length-preserving relative to the original text — recovering real character offsets for a Tier-1-only match would need a second, separate piece of engineering (position-tracking in Winnowing plus a stripped-position-to-original-offset mapping), not attempted here. Tier-1-only resolutions keep `matched_segments=None`, unchanged from before.

**Verification:** 16 new/extended unit tests across `test_tier2.py` (chunk-pair tracking, including a directly-tested invariant that a BM25-only-winning candidate — never a dense candidate — can never reach the structural-signal verify band at the deployed `ALPHA=0.6`, so the "no chunk pair available" case is provably close to unreachable rather than just assumed rare), `test_segment_extraction.py`, and `test_matched_segments_schema_roundtrip.py` (confirms the exact JSONB write shape validates against `SimilarityPairResponse`, the same path `submissions.py` uses to read it back out — this is the test that would have caught a field-name mismatch before it ever reached the Moodle report page). Also confirmed end-to-end with real data (not just mocked): a genuine Bayes'-theorem paraphrase pair from the evaluation corpus produced correct, sensible matched text and offsets on both sides, validated against the real Pydantic schema, not a synthetic fixture. A real, pre-existing test-isolation gap was found and worked around along the way: `FAISSIndex()`/`get_faiss_index()` with no explicit path loads a shared, persisted index file that accumulates vectors across the *entire* test session, not just one file — new tests asserting exact chunk-index behavior are sensitive to this in a way older, coarser tests never were; fixed by giving those specific tests an isolated `tmp_path`-based index rather than changing the shared fixture's global behavior.

This same chunk-pair-tracking capability was also the prerequisite for the structural signal's chunk-anchoring fix (Report 04's Addendum 7) — one underlying change served two independent features.

**For Chapter 4/5:** a ninth genuine finding, and a useful counterpoint to this report's framing so far — the first eight findings were all things that actively misbehaved (wrong data, security gaps, crashes, dangling references); this one is different in kind: a fully-built, silently-inert feature that never did anything wrong because it never did anything at all. Worth naming as a distinct failure mode in Chapter 5's methodology discussion: an audit looking only for incorrect behavior would never have found this, since there was no incorrect behavior to find — only an absence, visible solely by tracing the intended data flow end-to-end and noticing nothing writes to the one field the whole UI is waiting on.
